# Amazon OpenSearch Service 임시 배포 테스트

이 문서는 한 임시 도메인에 기본 Nori와 커스텀 Nori를 함께 설치했던 테스트의 기록입니다. 현재 [서비스 비교 실습](SERVICE_COMPARISON.md)은 도메인 A의 기본 Nori와 도메인 B의 커스텀 Nori를 비교합니다. 두 도메인에서 새로 실행한 결과로 이 기록을 해석하지 않습니다.

## 테스트 환경

2026년 9월 22일 서울 리전(`ap-northeast-2`)에 테스트 전용 도메인을 만들고, 로컬 빌드를 마친 ZIP을 수정 없이 배포했다. 기존 도메인에는 연결하지 않았다.

| 도메인 엔진 / 런타임 Lucene | OpenSearch 3.5.0 / Lucene 10.3.2 |

## 배포와 실행 결과

ZIP을 S3에 업로드한 뒤 `ZIP-PLUGIN`으로 등록했다. 패키지의 `AVAILABLE`, 도메인 연결의 `ACTIVE`와 구성 변경 완료를 각각 확인했다. 이후 SigV4로 실제 도메인 엔드포인트를 호출했다.

| 검사 | 결과 |
| --- | --- |
| 커스텀 패키지 검증과 도메인 연결 | 통과 |
| 기본 Nori와 커스텀 플러그인 동시 로딩 | 확인 |
| `_analyze` 요청 | 88건 모두 HTTP 200 |
| 커스텀 tokenizer와 로컬 기대값 비교 | 27건 모두 일치 |
| 기본 tokenizer와 사용자 사전 조건의 토큰/위치 비교 | 54건 모두 일치 |
| 인덱스 설정 및 등록 analyzer 검사 | 7건 모두 기대 토큰과 일치 |
| 샘플 상품 색인 | 4건 모두 성공 |
| `캠핑 의자` 검색 | `P002`, `구름결캠핑의자` 반환 |
| 분석, 색인, 검색을 포함한 서명 HTTP 요청 | 97건 모두 2xx |
| 임시 인덱스 삭제 | 완료 |

88건은 tokenizer 81건과 analyzer 7건의 합이다. 커스텀 tokenizer 27건은 9개 입력과 `none`, `discard`, `mixed`의 조합이며, 토큰 문자열, 왼쪽 품사, 시작/끝 offset, position, positionLength를 비교했다. 기본 tokenizer 27건과 기본 tokenizer에 사용자 사전을 적용한 27건은 같은 항목 중 품사를 제외하면 모두 일치했다.

실제 분석 요청은 한국 시간 13:35:43부터 13:35:51 사이에 수행했다. 이 시간은 도메인 생성과 플러그인 연결 대기 시간을 포함하지 않으며 성능 측정값도 아니다.

## 기본 Nori와 비교할 때의 차이

이 도메인의 AWS 제공 Nori는 `/_cat/plugins`에서 `opensearch-analysis-nori`로 표시됐다. 커스텀 플러그인은 `analysis-nori-commerce`로 표시됐고 두 플러그인이 함께 동작했다.

기본 Nori 관련 54건 중 30건은 로컬 기준과 품사 표기가 달랐다. AWS 응답에서는 조사 `JKB`, `JKO`, `JKS`, `JX`가 `J`로, 어미 `EC`, `EP`가 `E`로 표시됐다. 그 밖의 비교 필드에는 차이가 없었다. 커스텀 tokenizer는 품사를 포함해 27건 모두 로컬 기대값과 일치했다.

따라서 기본 Nori의 응답 전체가 로컬과 동일하다고 판정하지 않았다. 품사 차이는 별도 기록으로 남겼으며, 플러그인 연결 및 커스텀 분석 검증의 통과와 구분했다. 이 관측 결과를 다른 AWS Nori 패키지 버전에 일반화하지 않는다.

배포 테스트 준비 중에는 IP 조건에 따른 접근 거부, 도메인 생성 직후의 구성 변경 충돌, 기본 플러그인 이름 및 품사 표기에 대한 로컬 가정이 드러났다. 최종 검증은 IAM 주체를 제한하고 구성 변경 완료를 기다린 뒤 실행했다. 빌드 ZIP이나 커스텀 기대 토큰을 변경해 통과시킨 것은 아니다.

## 정리 상태와 범위

한국 시간 13:51:16에 별도 읽기 전용 AWS API 호출로 삭제 완료를 재확인했다. 최종 검증과 준비 중 재시도를 포함해 이번 작업에서 생성한 도메인 4개, 커스텀 패키지 4개와 S3 객체 4개가 모두 정리됐다. 각 실행 기록의 잔여 소유 리소스 목록도 비어 있다.

| 정리 대상 | 확인 방법과 결과 |
| --- | --- |
| 임시 도메인 | `DescribeDomain`에서 `ResourceNotFoundException`, 도메인 목록에도 없음 |
| 임시 커스텀 패키지 | `DescribePackages`에서 조회되지 않거나 `DELETED` |
| 업로드한 ZIP | 각 S3 키를 조회해 객체가 없음을 확인 |
| 기존 리소스 | 기존 도메인 2개, 기존 S3 버킷과 AWS 제공 Nori 패키지 보존 |

기존 도메인에는 설정 변경이나 패키지 연결을 요청하지 않았다. 기존 버킷의 공개 액세스 차단 설정 네 개가 모두 유지되고 버전 관리가 새로 활성화되지 않은 것도 확인했다. 테스트 중의 리소스 사용에는 비용이 발생할 수 있으며, 삭제를 확인했다고 이미 발생한 사용료까지 없어지는 것은 아니다.

원문 HTTP 응답, 계정 정보와 배포 실행기는 공개 소스에 포함하지 않는다. 로컬의 Git 제외 경로 `build/aws-deployment-validation/`에 증거를 보관한다. 공개 샘플의 빌드 명령이 AWS 리소스를 생성하도록 바꾸지 않았다. 당시 사용했던 로컬 `make verify-http`는 현재 실습에서 제거했다.

이번 검증은 low 비용 사전 ZIP 한 개의 배포와 소규모 기능 테스트다. high 비용 사전의 AWS 배포, Linux에서의 MeCab 네이티브 컴파일, 도메인 업그레이드, 부하 테스트, 장시간 안정성, 검색 품질 평가는 포함하지 않는다. 패키지 검증 통과를 보안 취약점 부재의 증명으로 해석하지 않는다.
